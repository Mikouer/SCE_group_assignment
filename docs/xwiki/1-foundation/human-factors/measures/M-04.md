# M-04: Interaction protocol conformance

| Field | Description |
| --- | --- |
| ID | M-04 |
| Name | Interaction protocol conformance |
| Status | In Progress |
| Evidence basis | Bespoke verification measure derived from the specified behaviour of [UC01](../../../2-specification/use-cases/uc01/UC01.md) and [TECH-02](../../technology/TECH-02.md), including the reminder, postponement, uncertainty, escalation, logging and closure branches. |
| Construct measured | Whether the prototype follows the specified interaction sequence, state transitions and timing in the defined scenarios. |
| Type | Quantitative. |
| Instrument or procedure | In a log-based run ([EM-03](../evaluation-methods/EM-03.md)) the prototype writes a timestamped event log. For each scripted scenario the log records the meal trigger, each reminder (number, time, channel), the response state, any postponement, the eating state (confirmed by the camera or by Cleber saying he is done, unconfirmed, or uncertain), the camera state (inactive until kitchen activity, then active until the meal is complete and while the escalation sequence is happening; it stays inactive when there is no kitchen activity), each escalation message and its recipient, the plate leaving and returning, the interaction closure, and the entries shown in Sarah's summary. In a cognitive walkthrough ([EM-04](../evaluation-methods/EM-04.md)) the source is instead the evaluators' recorded answers to the four walkthrough questions at each step of the Action Sequence, with their justifications. |
| Scoring or coding scheme | For each scenario, mark pass only if every required event and transition occurs in the specified order and at the configured intervals. Report the proportion of scenarios that pass, together with each deviation (wrong order, extra or missing reminder, prompt after closure, wrong recipient, a reminder sent while the plate is away, missing log entry). Also report descriptive timing data from the same log: reminders needed per episode, time from first reminder to kitchen entry, whether postponement was used, and plate-away duration. These support tuning the intervals and do not have a pass/fail threshold. For a walkthrough, record per step how many of the four questions were answered yes, and list every failure story and design suggestion; steps with any no are the findings. |
| Validity and reliability | Appropriate for verifying the prototype's scripted logic. The facilitator selects the meal-state events, so the measure does not establish the accuracy of real kitchen sensors or the camera, real meal consumption, speaker coverage across rooms, or any effect on a person. In a walkthrough it reflects evaluator judgement of the persona, not observed behaviour. |
| Serves | Verification. |
| Burden | Low; no human subjects are needed. |

Used by [EM-03](../evaluation-methods/EM-03.md) and [EM-04](../evaluation-methods/EM-04.md). It operationalises
[UC01-F1-PR1](../../../2-specification/use-cases/uc01/UC01-F1-PR1.md), [UC01-F2-PR2](../../../2-specification/use-cases/uc01/UC01-F2-PR2.md),
[UC01-F3-PR3](../../../2-specification/use-cases/uc01/UC01-F3-PR3.md) and [UC01-F4-PR4](../../../2-specification/use-cases/uc01/UC01-F4-PR4.md).
